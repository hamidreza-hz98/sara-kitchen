# Serverless-safe media processing (SK-0074)

The deployment ADR selects Vercel Node.js Functions. No background job service has been approved or provisioned, so launch processing is limited to **one small image per route invocation**. Video, PDF, and larger-image processing are unsupported for MVP; they must not be marked ready or exposed publicly. The technical format/size allow-list in `docs/media-upload-policy.md` is an upper bound for future direct-to-storage or worker flows, **not** permission to proxy 10–50 MiB through a Vercel Route Handler. The eventual SK-0075 upload route must surface the effective MVP limits in the UI and reject unsupported work before storing it.

| Boundary                     |                          MVP threshold | Enforcement                                                                                                                                              |
| ---------------------------- | -------------------------------------: | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Image payload                |                                  3 MiB | `processImageForRoute` checks actual Buffer length before decoding.                                                                                      |
| Entire HTTP body             |                                3.5 MiB | Future route and ingress must enforce byte count while streaming, including multipart fields.                                                            |
| Files per invocation         |                                      1 | Future route rejects bulk processing; bulk UI can submit separate requests with backpressure.                                                            |
| Decoded dimensions           | 8 million pixels; max 4000 px per side | Header preflight plus the image processor's stricter decode limits.                                                                                      |
| Per-instance concurrent jobs |                                      1 | In-process admission rejects additional jobs as `processing_busy`; no unbounded queue.                                                                   |
| Image transformation budget  |                              8 seconds | Deadline checked between sequential variants. Each Sharp variant has a native 2-second timeout.                                                          |
| Planned route maximum        |                             15 seconds | SK-0075 Route Handler must declare `export const maxDuration = 15` and reserve the remaining time for validation, storage, database write, and response. |

Four variants run **sequentially**, limiting simultaneous decode/encode memory. The 8-megapixel bound implies at most about 32 MiB for one 4-channel 8-bit decoded frame, but native library caches, intermediate buffers, encoding, and runtime overhead are additional and require production-equivalent measurement. The function must use the Node.js runtime, not Edge, and production load testing must verify p95 processing time and peak RSS under representative concurrent uploads before launch. If either exceeds the budget, lower thresholds or add an approved durable background worker; do not silently increase route duration or hold requests open.

`planMediaProcessing` reports `inline_image` or an `unsupported_mvp` reason without scheduling work. `processImageForRoute` performs a second check on actual input bytes and image header, owns the per-instance slot, and invokes the bounded Sharp pipeline. The route must still authenticate, authorize, apply CSRF/origin and upload policy, verify the input signature, enforce request-body limits before buffering, and clean up any partial private objects on failure. A timeout or busy result must leave no ready Media record; the route should return a retryable or clear unsupported response using the standard API contract. Never use an in-memory queue or fire-and-forget promise for persistent processing in a serverless function.

This choice deliberately defers video/PDF parsing and large-image work. A future durable worker should consume an idempotent job record after direct-to-private-MinIO upload, enforce CPU/memory/format limits, retry safely, and transition Media from pending to ready or failed. Worker selection and costs require explicit project approval.
