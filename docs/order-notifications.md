# Order notifications (SK-0157, delivery foundation)

Launch channel decision: employer WhatsApp; customer email is deferred. Customers receive localized, private in-app notices at `GET /api/profile/notifications` in the interim. The endpoint requires the customer's session and reads only that customer's records. Employer notification copy is English pending an owner-locale setting. Every message is plain text and contains only an order code and status; no address, telephone, payment secret, or free-form notes enter the queue.

The order state machine emits intents for receipt, payment confirmation/failure/expiry, fulfillment, cancellation, and confirmed refund. Checkout and each order/payment transition insert corresponding `order_notifications` records within the same MongoDB transaction as the order change. `(eventKey, intent)` is unique, so duplicate event handling does not enqueue duplicate messages. Customer in-app records become visible immediately after commit. Employer WhatsApp records remain `pending` until a configured sender acknowledges them. Failed sends never roll back a valid order.

`dispatchOrderNotifications()` is a bounded, lease-based worker contract. It requires an idempotent transport that recognizes a stable event/intent key. It retries with exponential backoff, records a generic error code without provider secrets, and moves a message to `dead` after five failures. `getOrderNotificationDeliveryHealth()` returns pending, in-flight, and dead counts for operations. Providers must be idempotent across an accepted-send/lost-acknowledgement case before their adapter is enabled; queue uniqueness alone cannot prevent that external duplicate. A production scheduler must invoke the dispatcher and alert on dead or ageing pending work.

Authorized order operators can inspect aggregate queue counts at `GET /api/orders/notifications/health`; no recipient or message content is returned.

Live WhatsApp delivery is deliberately **disabled**: the owner has not supplied a WhatsApp Business/Cloud API connection or approved outbound templates. Existing `WHATSAPP_ENABLED=false` must remain so. `WHATSAPP_API_URL`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_ACCESS_TOKEN`, and `WHATSAPP_EMPLOYER_NUMBER` belong in a deployment secret store, not a chat or repository. Once a provider and approved templates exist, add its adapter, authenticated scheduler, callback/acknowledgement handling, and end-to-end sandbox tests. Do not report queued messages as sent until the provider confirms them.

Validation: integration tests cover all three customer locales, in-app ownership projection, duplicate enqueue, transaction rollback, deterministic retries, dead work, and acknowledgement-only delivery. Checkout, management transition, and payment reconciliation tests assert no regression. This task remains open for actual WhatsApp sending and customer email; the queue is production-shaped but not a live channel.
