# Transaction management (SK-0156)

Customer checkout is the sole creation path. There is no admin transaction create or delete endpoint, and an admin cannot edit amounts, provider references, customer/order identity, or prior events. Financial records are append-oriented and retained. The Mongoose model rejects query updates/deletes, bulk writes, event rewrites/removal, and changes to the original requested amount; direct database access must remain restricted to trusted services.

`GET /api/transactions` and `GET /api/transactions/[transactionId]` require `transactions:read` and return bounded, sorted, paginated safe views. Provider references and internal notes require `transactions:read-sensitive`. Raw tokens, request payloads, signatures, event IDs, and provider bodies are never in this response. `PATCH /api/transactions/[transactionId]` requires `transactions:reconcile` and changes only a bounded internal note with an expected management revision and audit event.

`POST /api/transactions/[transactionId]/reconcile` fetches status from the provider. It checks provider payment/request IDs, currency, original amount, all resulting amount fields, and state-machine legality before appending an event. No admin-supplied payment status or amount is accepted. `POST .../cancel` and `POST .../refund` require an `Idempotency-Key` header, permission, provider capability, and provider-confirmed result. Refund is owner-only. All three actions update the linked Order through its public API and write English audit records in the same replica-set transaction. A failed Order synchronization rolls back the Transaction change. Reconciliation of an already matching status can heal a previously unsynchronized Order without duplicating the payment event.

The local MB Way sandbox is an in-process simulator, shared across development route handlers only. It cannot act as a production payment rail or a durable cross-process source of truth. Its automated refund capability is disabled. A phone-support request is not proof of a completed refund: the order and transaction must remain in their actual financial state until an approved provider can verify the refund. Future live providers must implement the same interface and validated state transitions; do not enable a manual status override merely to satisfy a support request.

All mutations require an authenticated admin, a matching permission, same-site/CSRF protection, strict Zod input, and no-store responses. Conflict, unsupported operation, uncertain provider result, and missing record produce typed API errors. Tests cover role restrictions, safe note edits, successful and repeated reconciliation, provider amount mismatches, cancellation, refund permission/capability, append-only history, and rollback/recovery when linked Order synchronization fails.
