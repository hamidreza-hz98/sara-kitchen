# MB Way sandbox webhook (SK-0151)

`POST /api/payments/mbway/webhook` is an **internal local-simulator** endpoint, not a live MB Way PSP callback. It is disabled in production. A selected acquirer must supply its documented signature, status, event-ID, retry, and certification rules before a live endpoint is enabled. No checkout payment is charged by this task.

The route accepts only bounded (4 KiB), valid UTF-8 JSON. It authenticates the exact raw body with `x-mbway-signature: sha256=<hex HMAC>` over `<x-mbway-timestamp>.<raw body>` using `MBWAY_WEBHOOK_SECRET`, then checks the ten-digit Unix timestamp within five minutes. It validates a strict safe-data schema **after** signature verification. It never logs or stores the body, signature, secret, phone, or card-like references. Invalid/missing signatures return 403; oversized or malformed bodies are rejected. The signed webhook is exempt from browser CSRF/origin checks.

Every verified event first enters `payment_webhook_events` as `received`, keyed uniquely by `(provider, providerEventId)`. A repeated identical event is idempotent; reuse of the ID with different verified fields returns 409. Processing loads the matching MB Way sandbox Transaction by safe provider payment ID. A MongoDB replica-set transaction atomically appends the payment state event and marks the inbox item `applied`, or marks a valid but regressive/invalid transition `ignored` with a reason. Unknown payment references leave the inbox `received` and return 503 so delivery can be retried. Failure or database transaction unavailability also returns 503; no provider network call or notification is performed inside the request. Retrying the same signed event resumes a `received` record. A manual/automated reconciliation worker can later scan the indexed `received` records if the provider exhausts retries.

An applied webhook updates the Transaction, matching Order status/history, sold-count projection when applicable, audit record, and durable inbox within one MongoDB transaction. If any write fails, the inbox stays `received` for retry. A real provider transport remains future work; production checkout stays fail-closed until a certified adapter is configured.

Integration tests use a real one-node MongoDB replica set and cover tampered/stale signatures, unsafe data, valid capture, duplicate and conflicting IDs, out-of-order status, unmatched references, and injected rollback/retry.
