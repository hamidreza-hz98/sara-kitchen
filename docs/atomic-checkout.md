# Atomic checkout (SK-0154)

`POST /api/checkout` accepts a customer session, a same-origin JSON request, and a stable `Idempotency-Key`. The browser supplies a cart version, MB Way mobile, and the two accepted policy IDs/versions; it supplies no price. The server requires the MB Way mobile to match the customer's registered Portuguese mobile, avoiding a second persistent payer-phone field.

Within one replica-set transaction, Orders re-reads the active customer cart, customer identity, owned delivery address, dish availability, dish purchase snapshots, current published contact/delivery settings, and current published policies. It checks pickup/delivery eligibility, quantity and lead time, computes integer-cent prices from current dish records and delivery bands, and rejects a changed total for re-review. It then creates an immutable Order and created Transaction, writes both append-only order-policy consent receipts, writes an Orders-owned initiation/recovery record, converts the cart, and commits a 30-day idempotent result. Any pre-commit error rolls back all of these writes. A standalone MongoDB server fails closed before the callback runs.

Only after commit does the request atomically claim the `ready` initiation record and call the provider with a stable key derived from the order ID. A known pending provider response updates the Transaction and marks initiation `complete`. A timeout, lost response, or persistence failure leaves `in_flight` or `needs_reconciliation`; the API returns the original order and never automatically initiates again. Operators must reconcile the provider reference/status and the matching Transaction before any further payment attempt. Query `checkout_initiations` by `state` and `attemptedAt`; the unique `orderId` index prevents duplicate intents. No raw payment token, API secret, or extra payer mobile is stored in this collection or the idempotency result.

The current adapter is an **in-memory local MB Way simulator**, enabled only outside production when `MBWAY_ENABLED` is configured. Production remains fail-closed until a durable, provider-backed MB Way transport and operator reconciliation are approved. The storefront review button remains disabled until SK-0160 provides a verified payment-result experience; the backend can be exercised directly in a configured local sandbox. Notifications and later order transitions belong to SK-0155–SK-0157.

The replica-set tests cover authoritative pricing, replay without a second provider call, conflict on reused keys with different payloads, full rollback before commit, immutable consent receipts, and uncertain provider recovery. Docker Desktop is not required for these tests because they use an in-memory replica set.
