# Idempotency contract (SK-0044)

The Transactions module owns `idempotency_records` and exposes `runIdempotentOperation()`. Checkout (Orders), payment initiation, and verified provider webhooks call this public API. A record is identified by `(scope, subject, key)`, where scope is `checkout`, `payment`, or `webhook`, and subject is the authenticated customer ID or provider account identity. Checkout keys come from a client-generated high-entropy token; webhook keys come from a stable, verified provider event ID. A key must be 8–128 safe characters. Neither keys nor fingerprints replace actor authorization or provider signature verification.

The request fingerprint is SHA-256 of bounded canonical JSON: object keys are sorted, array order and values remain significant, and non-JSON/oversized input is rejected. It is calculated from the normalized business command, including the target order or relevant actor context; avoid raw secrets and volatile transport metadata. Same identity and fingerprint replays the committed result. Same identity with a different fingerprint is a 409 conflict. Separate subjects/scopes can reuse a textual key safely.

Route adapters should supply locale-specific `messages` from `errors.idempotency` when invoking the service; all three launch catalogs contain the conflict and in-progress messages. The service otherwise returns the generic API conflict message.

`runIdempotentOperation()` inserts a pending record, invokes the session-bound workflow, and stores the JSON result with `completed` status **inside the same MongoDB transaction**. Only a committed record is visible to another request. A failure rolls back both the idempotency record and all participating business writes, allowing a retry. The unique compound index arbitrates concurrent requests; a losing identical request reads and returns the winner's result. A callback may execute more than once because MongoDB can retry a transaction or a concurrent attempt can later roll back. It must use the supplied session for every write and never call MB Way, WhatsApp, MinIO, or any other external side effect. Post-commit work is driven by outbox records created in the same transaction.

Results must be small JSON-safe DTOs (at most 64 KiB), not raw Mongoose documents, access tokens, or sensitive provider payloads. The idempotency record is private persistence, not an API response. The caller chooses the final HTTP envelope and returns the stored result on replay. Production index provisioning must create the unique `(scope, subject, key)` index and TTL index on `expiresAt` before accepting traffic; indexes are declared on the private model. Retention is 1–30 days, chosen by the workflow. Use at least 48 hours for checkout and a provider-appropriate longer window for webhooks. TTL cleanup is asynchronous, so an expired record may remain and continue to replay until MongoDB deletes it; after deletion, the same key can initiate new work. Provider event IDs also need a durable unique constraint in the eventual payment-event collection for replay safety beyond the TTL window.

The existing standalone local MongoDB cannot run these workflows. Replica-set integration tests cover identical retries, conflicting reuse, per-subject isolation, rollback, and concurrent webhook delivery. When the actual order/payment endpoints are built, add Route Handler tests for their key header/body contract and translated conflict presentation.

References: [MongoDB unique indexes](https://www.mongodb.com/docs/manual/core/index-unique/), [MongoDB TTL timing](https://www.mongodb.com/docs/manual/core/index-ttl/), and [Mongoose transaction retry/parallelism guidance](https://mongoosejs.com/docs/transactions.html).
