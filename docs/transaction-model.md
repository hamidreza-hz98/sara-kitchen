# Transaction model (SK-0147)

`Transaction` is a provider-neutral financial record owned only by the Transactions module. It references an Order and Customer by ObjectId, but never imports either model. The initial integration uses `mbway` with `mbway-sandbox`; reserved method/provider pairs allow PayPal, card-gateway, and manually settled cash later. Supporting a new provider requires an explicit enum/schema change and adapter, not arbitrary provider strings.

All money is non-negative, bounded, safe integer **EUR cents**. `requestedCents` is the immutable charge basis; `authorizedCents`, `capturedCents`, and `refundedCents` are snapshots of settled state. Authorization and capture each cannot exceed the request; refunds cannot exceed captured funds. Captures without a prior authorization are permitted for direct-settlement methods. State transitions and provider-event mappings are intentionally SK-0148, not inferred from this schema.

`idempotencyKeyHash` is a SHA-256 digest of a scoped key, never the bearer key. It is unique and excluded from ordinary queries and JSON. Optional provider request/payment IDs are bounded opaque references; the provider payment ID is unique only when present. They are excluded from ordinary queries and JSON. Response codes are short uppercase machine codes, not provider bodies or human-readable free text. The schema rejects unknown root fields, strips unknown nested fields, and disallows long numeric runs in references to reduce accidental payment-card storage. No PAN, CVV, phone number, provider credential, or raw gateway payload belongs in this collection.

Each transaction starts with a `created` event and its latest event must match the current status. Events carry a local event key, source, resulting status, optional amount, safe response code/provider event ID, and occurrence/record times. Keys and provider event IDs are unique within the transaction. Existing events cannot be edited, reordered, or removed via document validation or save, even when normal validation is skipped. Query mutations, deletions, and bulk writes are blocked; the future repository must load the document and append via `save()` with optimistic concurrency. The MongoDB collection API or direct database access can bypass Mongoose middleware, so database write credentials must remain confined to trusted services. Audit logs remain separate; this event history is the payment lifecycle, not a replacement for audit records.

Indexes support unique idempotency and provider payment lookup plus order, customer, and status timelines. There is no TTL: financial records need an explicit retention policy. Order creation and the first transaction write will be atomic under the Orders-owned checkout transaction (ADR 0008). External gateway calls never occur inside that MongoDB transaction.

Verification: `tests/unit/transaction-model.test.ts` checks shapes, money/privacy invariants, and indexes; `tests/integration/transaction-model.test.ts` checks persisted uniqueness and append-only write guards.
