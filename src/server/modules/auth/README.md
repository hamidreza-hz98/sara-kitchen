# Auth

Owns credential verification orchestration, login, logout, signup coordination, password reset/change flows, and actor resolution. It may consume the public APIs of Admins, Customers, and Sessions. Password hashes remain owned by the relevant identity module; session persistence remains owned by Sessions.

SK-0052 implements administrator login/logout. The identifier is normalized by Admins, password verification remains in Admins, and Sessions issues a fresh 256-bit opaque bearer on every successful login. An incoming admin bearer is revoked before the new one is issued (fixation defense). The login result never includes the raw token in JSON; only the Route Handler sets it in an HttpOnly, SameSite=Strict, host-only cookie. Production uses `__Host-sara_admin` with Secure; local HTTP uses `sara_admin_dev`. The login endpoint requires a same-origin `Origin` header and gives the same generic credential error for wrong/unknown/disabled accounts. Logout revokes the current bearer and clears the cookie. The dashboard resolves an active admin only after checking session audience, absolute/idle expiry, revocation and password version. No default admin is created by this flow.

SK-0058–SK-0060 add reusable route/action permission guards, CSRF defenses, and shared MongoDB rate limits. Each future business endpoint must still apply the exact permission and operation-specific controls. Initial administrator provisioning remains a launch prerequisite.

SK-0053 adds `POST /api/auth/customer/signup`. It requires a same-origin `Origin`, validates and normalizes all inputs, applies a MongoDB-backed fixed-window limit (30 attempts per source IP and five per mobile and optional email per hour), then asks Customers to register. The endpoint returns the same `202 {accepted: true}` for new and duplicate mobile/email identities, does not issue a session, and never includes account data in its response. Rate-limit keys are HMAC-SHA256 digests using the server-only session secret; neither IP nor identifier is stored in the limiter. The `signup_limits` collection has a unique key index and TTL expiration. Vercel overwrites `X-Forwarded-For`; a different deployment proxy must overwrite it too before production. If no valid address arrives, attempts share an `unknown` bucket (fail-closed). TTL cleanup is asynchronous, while enforcement always uses the atomic counter and fixed window. Password hashing runs for both new and duplicate identities.

SK-0054 adds customer login/logout/session-status Route Handlers and a protected `/profile` subtree. The customer cookie has its own audience and name; it never grants admin access. Login accepts normalized mobile or email, consumes a dummy Argon2id verification for unknown/disabled identities, and returns one generic 401 for wrong, unknown, or disabled credentials. Existing customer bearers are revoked during login rotation. The fresh opaque bearer is sent only in an HttpOnly, host-only, SameSite=Strict cookie; production adds Secure and the `__Host-` prefix. A normal session uses a browser-session cookie, 12-hour absolute lifetime, and 30-minute server-enforced idle timeout. Explicit “keep me signed in” uses a 30-day persistent cookie/absolute lifetime and seven-day server-enforced idle timeout. Logout revokes the bearer in MongoDB and expires the browser cookie; the no-secret session endpoint exposes only authenticated state and display name. The storefront broadcasts only a non-sensitive invalidation signal through local storage so other tabs refetch session truth and refresh protected routes. SK-0059 and SK-0060 subsequently add CSRF and login-throttling controls.

SK-0055 adds customer `/forgot-password` and `/reset-password` screens and `POST /api/auth/customer/password-reset/{request,complete}`. A request accepts mobile or email but always delivers to the registered mobile through the Twilio SMS adapter; a valid response is the same generic 202 regardless of account existence. The bearer is a 256-bit random URL-fragment token, HMAC-hashed in MongoDB, valid for 15 minutes, and superseded by a newer request. The browser removes the fragment immediately. Completion atomically consumes the token, updates the Argon2id hash and password version with a compare-and-set, revokes every customer session, and clears the current customer cookie. MongoDB-backed IP and identity throttles protect requests and submissions; keys are HMAC hashes, not raw identifiers. The deployment proxy must overwrite `X-Forwarded-For`. Provider credentials are never committed; see `docs/environment.md`. Administrator recovery is not covered by this customer-only flow and needs a separate verified-contact policy before enabling it.

SK-0056 adds the protected customer `/profile/change-password` page and `POST /api/auth/customer/change-password`. It verifies the current password, applies the same 15-character passphrase policy as signup/reset, rejects reuse, and compare-and-set increments the password version. The current bearer is always revoked and replaced with a fresh opaque bearer while retaining its original absolute expiry and persistence choice. The checkbox defaults to revoking every other session. If the customer unchecks it, only other active sessions at the previous password version are advanced to the new version, so they genuinely remain signed in. A failure after the credential update fails closed: older-version sessions cannot authenticate. Administrator change password is not part of this customer flow. SK-0060 subsequently adds actor/IP credential-attempt throttling.

SK-0057 adds owner-scoped `GET` and `POST /api/auth/{admin|customer}/sessions` with protected dashboard and profile pages. `GET` lists 20 active sessions per page with coarse browser/platform labels, timestamps, persistence, and a current-session marker. Neither raw bearer, user-agent, nor IP is returned; responses are `no-store`. `POST` requires a same-origin request and accepts either `{action: "one", sessionId}` or `{action: "others"}`. Individual revocation cannot target the current bearer or another actor's session; the existing logout endpoint handles the current device. Bulk revocation excludes the current bearer. Revocation is persisted server-side and takes effect on the next protected request. Both admin and customer identities must still be active and have matching password versions before managing sessions.

SK-0058 adds server-only `requireAdminActor`, `requireCustomerActor`, `requireCustomerOwnership`, and `requireDashboardActor` guards. Each resolves the database-backed session and current active identity; admin permissions come from the fixed role matrix, never a client claim. Dashboard paths have an explicit read-permission mapping; unknown paths fail closed. The server page adapter redirects absent/expired sessions to login and masks forbidden or unknown dashboard paths as 404. Server Actions must authorize independently of page layouts. The active-session bulk-revocation action demonstrates this: it re-resolves the principal before changing state. Future API handlers and actions must check action-level permission and object ownership at their own entry point; hiding a dashboard link is only a usability feature.

SK-0059 layers strict Origin/Host/forwarded-header and Fetch Metadata checks over every browser mutation. Authenticated JSON mutations also require a session- and principal-bound `X-CSRF-Token` issued by the no-store `/api/auth/csrf` endpoint after active actor resolution. Production session cookies remain host-only, HttpOnly, Secure, and SameSite=Strict. Public authentication/recovery mutations cannot have a session synchronizer token, so they use the strict origin boundary. Next.js's native same-origin Server Action check has no configured bypass; actions continue to authenticate internally. See `docs/request-security.md`.

SK-0060 adds shared MongoDB rate limits to admin/customer login and sensitive account operations, while retaining and extending the signup and password-reset limits. IP buckets and normalized identifier or authenticated-actor buckets are independent. Opaque HMAC keys prevent persistence of source addresses, identifiers, actor IDs, and reset bearers. Every known and unknown login/recovery identity follows the same limiter and generic error path. The shared 429 contract rounds `Retry-After` to minutes and never identifies the fired bucket. A future verification flow must call the exported verification limiter before identity lookup. Thresholds and deployment proxy requirements are recorded in `docs/authentication-rate-limits.md`.
